# REPORT — A5 · resources as constrained objects

**23 August 2026.** `BUILD_SEQUENCE_KIRO.md §A5`, `RESOURCE_MOVEMENT_MODEL.md §2 · appendix`,
`DEMO_PLAN_V2.md` criteria 16 · 19 · 20.

**Status: ✅ GATE GREEN.** 19/19 in the new suite, **293/293 across 16 files** with A5 applied.

`btree_gist` was installed in `0001` for exactly this and had never been used. It is used now: a
vessel or a machine committed twice over the same window is no longer a warning to be rendered — it
is **a row that cannot exist**.

Both tables carry `during tstzrange generated always as (tstzrange(started_at, ended_at)) stored`, so
the window can never disagree with the timestamps it was built from. An **open** stint
(`ended_at is null`) becomes unbounded above — the machine is still busy and blocks everything after
it. That is the correct reading of an unclosed stint, not a gap.

## 2. Criterion 16 — refused by the constraint, *not by the form*

> *"Assigning one turner to both T1 and T2 on the same pile is refused by the `machine_usage`
> exclusion constraint, not by the form."*

The criterion names the mechanism, so the proof asserts the mechanism. A test that only checked "the
second insert failed" would pass equally against a trigger, a form check or a unique index — none of
which is what §A5 asked for. So the assertion reads the error:

```ts
expect(why).toMatch(/machine_usage_no_overlap|exclusion/i);
```

and a separate test reads `pg_constraint` and requires `contype = 'x'`, `EXCLUDE USING gist` and
`during WITH &&` on both tables.

**Everything runs as `postgres`.** That is deliberate, and it is the strongest available position:
`postgres` has `BYPASSRLS` and every privilege there is, and it still cannot write an overlapping row.

`TURNER_CLASH` is **kept** in `validate_batch` as well. The constraint refuses the second stint at
write time; the plan-time check catches the intent before anyone tries, which is what an admin filling
a form needs. Two checks, two moments, one truth — not a heuristic standing in for a constraint.

## 3. Criterion 19 — a bunker serves both streams

> *"Storing paddy in Bunker 4 blocks a compost occupancy of Bunker 4 in the same window."*

The exclusion constraint does not care which stream is asking. `RESOURCE_MOVEMENT_MODEL §2` —
*"a paddy occupancy blocks a compost occupancy exactly the same way"*. `stream` and `material_state`
are recorded because §2's occupancy record carries them and the Gantt renders a column per stream;
they do **not** appear in the constraint, so they cannot weaken it.

## 4. Criterion 20 — no editable hours field anywhere in the schema

> *"Machine utilisation for the batch is derived entirely from `machine_usage` — no editable hours
> field exists anywhere in the schema."*

`machine_usage.minutes` is `generated always … stored`, and a direct write is refused in Postgres's own
words, asserted verbatim rather than as `/generated/i`:

```
column "minutes" can only be updated to DEFAULT
```

**The first version of this proof was wrong, and finding out was worth the run.** A regex for
`(^|_)hours?$` returned eight hits and the test went red. None was a violation:

| column | what it is |
|---|---|
| `batch_activity.baseline_start_hour` · `baseline_end_hour` | an hour **position** on the 552-hour axis |
| `process_activity.standard_start_hour` · `standard_end_hour` | same |
| `factory_clock.h0_hour_of_day` · `h0_minute_of_hour` | H0 itself |
| `v_batch_event.batch_hour` · `v_variance_contributor.baseline_start_hour` | same, in a view |
| `machine.meters_hours` | **boolean.** `MACHINE_UTILIZATION_MODEL` — whether the machine has an hour meter **fitted**. It holds no reading. |

Criterion 21 *requires* the axis columns. `meters_hours` is a capability flag. Criterion 20 forbids a
**quantity of machine time somebody types**, and none of these is one — so the schema was right and
the scan was wrong.

The repair is not a narrowed regex. A pattern tuned until it returns nothing proves nothing. There
are now two assertions:

1. **The sharp end.** No writable numeric column exists on `machine`, `machine_usage` or
   `location_occupancy` at all. Anything a person could type a 6.5 into on a resource table would be
   asserting utilisation the windows do not support.
2. **An allow-list, by name.** All 17 hour-named writable columns are enumerated and each classed
   `AXIS`, `PLAN` or `CAPABILITY`, with the classification itself checked — a `CAPABILITY` must be
   boolean, so it cannot quietly become a reading. A migration that later adds `machine.hours_used`
   changes the list and turns the test red.

`process_definition.baseline_hours` — the one aggregate hours figure in the schema — is asserted
`is_generated = ALWAYS`.

## 5. The ±2-day heuristic is gone

`0011` blocked a batch whenever another active batch's activity had a `planned_start_at` within
±2 days on the same destination:

```sql
and ob.planned_start_at between ba.planned_start_at - interval '2 days'
                            and ba.planned_start_at + interval '2 days';
```

`0011`'s own comment said *"A5 replaces this heuristic with an exclusion constraint."* It is a guess in
both directions: it blocks batches that do not clash and misses clashes outside the window. **It also
bit during staging** — it refused a demo batch that was fine.

What `validate_batch` reports now is what it can honestly know:

| severity | code | when |
|---|---|---|
| **blocking** | `VESSEL_DOUBLE_BOOKED` | an occupancy that is **recorded** and overlaps another active batch's. Evidence. |
| **warning** | `OCCUPANCY_NOT_RECORDED` | a vessel-bound activity with **no** occupancy on record, naming TBD-28 and TBD-29 |

The warning is the important half. The absence of a check is now **visible** instead of silent, and it
says why it cannot know. A test asserts `interval '2 days'` is no longer in the function body, and
another asserts two *adjacent* windows produce no clash — the false positive the heuristic generated.

`0021` re-creates `validate_batch` from `0011` **with one block changed**, everything else
byte-identical, stated in the migration header. Same reason `0020` gave for re-creating
`evaluate_gates`: patching a function body with `pg_get_functiondef` + `regexp_replace` + `EXECUTE`
is opaque and fragile, and extracting a helper still requires re-creating the call site.

## 6. What A5 did NOT decide — TBD-28, TBD-29, TBD-33

§A5: *"Blocked on TBD-28 / TBD-29 / TBD-33. Model both readings as configuration; do not choose."*

`resource_policy` carries **four rows** — both readings of TBD-28, both of TBD-29 — every one
`is_enabled = false`, each with its `source_ref` and the `consequence` of adopting it, so the choice is
made with its cost visible.

| question | reading | consequence if adopted |
|---|---|---|
| TBD-28 | `PADDY_HOLDS_BUNKER` | the compost bunker pool shrinks by one per concurrent batch |
| TBD-28 | `PADDY_SHARES_BUNKER` | pool unchanged; a real soak/fill clash goes undetected |
| TBD-29 | `RELEASE_AT_UNLOAD_START` | bunker free ~5 h earlier; two batches recordable in one bunker |
| TBD-29 | `RELEASE_AT_RELOAD_END` | safe; each batch holds a bunker ~5 h longer |

A partial unique index makes the ambiguous state **unwritable**:

```sql
create unique index uq_resource_policy_one_enabled
  on public.resource_policy (question_id) where is_enabled;
```

Enabling a second reading of one question is refused. A test does exactly that and asserts the refusal.

**`record_occupancy(activity, null, …)` REFUSES** and names the question rather than deriving a
window:

> *"A window is required. Deriving one needs the bunker release rule, and that is unanswered — TBD-29
> asks whether the source bunker is released at the start of the unload or at the end of the reload.
> Both readings are in `resource_policy`; neither is enabled."*

An explicit window is accepted and the constraint enforces it. Nothing defaults. A batch does not
silently acquire a bunker-release rule because a migration picked one.

**TBD-33 is not modelled as a policy at all.** The fleet is `machine` rows, and the constraints work
against whatever fleet exists. Inventing turners to make T1 ‖ T2 satisfiable is what rule 2 forbids.
The fleet on file is **11 machines, 2 TURNER, every row carrying `tbd_marker = 'TBD-33'`** — proved by
reading `0021` and asserting it contains no `insert into machine` and no `update machine`, which holds
however many times the seed is replayed. `machine` carries no timestamp, so this could not be proved
by time.

## 7. `MACHINE_STINT_CLOSED` started biting

B1 evaluated the rule as written — *"no open stint may exist"* — behind a check for the table's
existence, and said in `0012`'s header that **38 enabled `dictated` exit rules** would start biting the
moment A5 created it. They do.

`tests/gates.test.ts` ended with the honest record of the old world:

```ts
expect(exists.present, 'machine_usage belongs to A5 and is not built').toBe(false);
```

That was **the one red test** in the first full run after A5 — 292/293. It was **rewritten, not
deleted**: deleting it throws away the claim, and the claim has two sides. `tests/resources.test.ts`
proves the open → `fail` → closed → `pass` transition. What `gates.test.ts` now proves is what only it
knows — the predicate is **scoped to one activity** (`mu.batch_activity_id = ba.id`), so one machine
left running holds that activity and **not** the others. A predicate that read the table without the
scope would pass the transition proof and fail this one.

`machine_usage.batch_activity_id` and `ended_at` are therefore **a contract with the gate engine since
`0012`**, not a shape chosen here. The migration header says so.

## 11. Left undone

- **No occupancy is recorded for the three staged demo batches.** Doing so needs a window, and a
  window needs TBD-29. So every staged batch now carries `OCCUPANCY_NOT_RECORDED` warnings — which is
  the honest state, and the reason the warning was built rather than a derived window. It resolves the
  moment the factory answers TBD-29.
- **`open_machine_stint` / `close_machine_stint` are not called from `submit_activity`.** Binding a
  stint to a submission is a workflow decision the specs are silent on: whether closing an activity
  closes its stint, and what happens when the machine keeps running into the next activity. Not
  chosen here.
- **No UI.** `v_machine_utilisation` and both occupancy tables have no screen yet.
  `UI_IMPLEMENTATION_PLAN §S13` is the Resource Board and depends on this; `UI_DATA_CONTRACTS §14`
  already specifies `MachineLoad.hours` as derived.

## 12. Stop and ask

**One question, and it is not blocking A5.** `record_occupancy` accepts an explicit window from the
caller. Nothing in the specs says **who** may state one. The role model is silent on occupancy, so the
RPC currently accepts any authenticated caller and the `tbd_marker` records that the boundary was
caller-supplied rather than derived from a stated rule. If occupancy is a supervisor's statement rather
than an operator's, say so and it becomes a role check.
