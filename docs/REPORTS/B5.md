## 3. Exit proof 1 — a retest supersedes, the original survives

`LAB_MODEL §5`'s own worked example, run for real:

```
lab_result v1   moisture_pct 76.4   verdict FAIL   (frozen band 72.5–74)   superseded_by → v2
lab_result v2   moisture_pct 73.8   verdict PASS   reason post_corrective_action   supersedes → v1
```

`v_lab_result_history` returns **both rows**, v1 still carrying `fail`, v1 pointing forward at v2 and
v2 pointing back at v1. `v_lab_result_current` returns **exactly one head**. So *"MC 76.4 → 73.8
(retest)"* is renderable from the view alone, which is what §5 requires of the timeline and of every
decision package.

Four structural guarantees back it:

| guarantee | mechanism |
|---|---|
| overwriting is not a code path | `record_lab_result` refuses a second first result, naming the retest |
| a retest carries a reason code | `lab_result_retest_needs_reason` — `(version > 1) = (retest_reason is not null)` |
| v1 supersedes nothing | `lab_result_v1_supersedes_nothing` — `(version = 1) = (supersedes_result_id is null)` |
| one live head per test | `uq_lab_result_one_head`, partial unique index |

**The exit proof found a real defect on its first run.** `order_retest` inserted the new version and
*then* demoted the old head, so two unsuperseded rows existed at the end of the insert statement and
`uq_lab_result_one_head` refused **every retest**. A partial unique index is checked per statement
and cannot be deferred, so the fix inverts the order: pre-generate the id, demote the old head, then
insert. That means pointing at a row that does not exist yet, so `lab_result_superseded_fk` is now
`deferrable initially deferred`. The reasoning is written into the migration beside the index.

**An operator cannot make a failing number go away.** `order_retest` refuses any role other than
`lab_tech` and `supervisor`, per `ROLE_AND_APPROVAL_MODEL`'s matrix and §5's own sentence. Proved in
both directions — an operator is refused, a supervisor succeeds — by setting
`request.jwt.claims` for the transaction, which is what `current_app_role()` reads in production.

**The escalation threshold is data.** `LAB_MODEL §5` states *"more than 2 retests … escalates
automatically to the GM"*. The 2 is sourced, but a sourced number in a function body is still a
hard-coded count (rule 4), so it lives in `lab_setting.retest_escalation_above` and a test asserts
`order_retest` reads it rather than comparing against a literal.

## 4. Exit proof 2 — no spec means `no_spec`, and `no_spec` never fails

`verdict` is a **generated column**. It cannot be written, so no client can assert a pass — a test
tries and gets `column "verdict" can only be updated to DEFAULT`. The branch order *is* the refusal:

```sql
when invalid_reason is not null              then 'invalid'   -- declared unusable is not a fail
when target_min is null and target_max is null then 'no_spec'  -- TBD-13. NEVER auto-fails
when value_numeric is null                    then 'invalid'   -- a limit cannot judge an absence
when inside the band                          then 'pass'
else                                               'fail'
```

`no_spec` is checked at −5, 0, 0.001, 73 and 999999 on `TUNNEL_LOAD.ec` — the seeded null-null
`lab_spec` row — and is `no_spec` every time. Under any invented band, 999999 would fail.

**Two different silences, kept apart.** `spec_found` distinguishes them, and both give `no_spec`:

| | `spec_found` | meaning |
|---|---|---|
| `TUNNEL_LOAD.ec` | `true` | the spec row **exists** and states no bound — TBD-13, a factory question about a band |
| an unmapped checkpoint | `false` | there is **no spec row to read** — TBD-36, a question about a mapping |

**A band with no number is `invalid`, not `fail`.** Calling it a fail would invent a judgement about
a measurement nobody made. This mirrors `evaluate_gates`' `unevaluable`; `invalid` is the only member
of `LAB_MODEL`'s four-verdict enum that means "this cannot be judged".

**The freeze holds against a spec change.** A test records 76.4 as `fail`, then widens
`lab_spec` to 70–80 so it would now pass. The result's frozen `target_max` is still 74 and its verdict
is still `fail` — `LAB_MODEL §2`: *"Changing a spec must never silently re-judge a historical
result."* A retest at the same value gets the same band and the same verdict, which is what makes v1
and v2 comparable at all.

**`verdict` is text with a CHECK, not an enum, and that was forced.** A generation expression must be
IMMUTABLE; `text::enum` goes through `enum_in`, which Postgres marks STABLE, so
`case … end::lab_verdict` is rejected with *"generation expression is not immutable"*. A checked text
column gives the identical closed domain, and the rest of the schema already prefers that shape.

## 5. C-33 — both checkpoint maps, carried

```
LAB_DICTATION   27 checkpoints   24 with a stated day    0 mapped to a spec
S4B_COLUMNS     18 checkpoints    0 with a stated day    3 mapped to a spec
```

**All 45 rows carry C-33**, and that is not laziness. `CONTRACT_AUDIT §2.E` disagrees at Day 0,
Day 1, Day 4, the soaks, the nitrogen source, Day 8, Day 12, Day 15 and Day 22 — every point either
map describes. **A row left unmarked would be claiming the maps agree somewhere, and they do not.**

**Markers are a junction table, not a column.** One checkpoint routinely touches two open questions
at once — every row is C-33, *and* the Day-8 turnings are TBD-42, *and* the height rows are TBD-46. A
single `conflict_id` column would silently drop one, and rule 1 says carry both.

| marker | checkpoints | why |
|---|---|---|
| **C-33** | 45 | every point in both maps |
| **TBD-36** | 42 | no source states which `lab_spec` checkpoint this maps to |
| **TBD-46** | 4 | bunker / tunnel / shrunken height — lab or operational? |
| **TBD-42** | 3 | Day-8 moisture: per pass or per pile per pass? |
| **TBD-12** | 3 | sensory attributes, recording-only |
| **TBD-45** | 2 | dry weight, in the dictation with no column and no parameter |
| **TBD-13** | 2 | compost EC has no band |
| **C-01** | 1 | §11.2 branches on a moisture threshold it does not state |

**The proof that they were not merged:** tunnel loading exists in both maps under different codes
with different parameter panels — `DURING_TUNNEL_LOADING` (dictation, Day 15) and `TUNNEL_LOAD`
(S4b, no day). A merge would have collapsed them. And **a sample records which map it was filed
under**, so while C-33 is open that provenance travels with every number.

**Only three mappings to `lab_spec` were made**, and only because the code is byte-identical in both
vocabularies: `TUNNEL_LOAD`, `COMPOST_OUT`, `GR_LOAD`. TBD-36's own `ship_with_default` says *"Map
the unambiguous ones; leave the rest unmapped and visible"* — so this is the registered interim
behaviour, not a choice made here.

**A fourth vocabulary already existed and is left alone.** `lab_spec` uses S4a *phase* names
(`FIBRE_WETTING`, `TURNING_0_1`, `RELOADING`, nine typed `WATER_*` codes) and overlaps S4b's on three
only. Nothing here reconciles them.

**Two codes were de-materialised.** `LAB_MODEL §3` writes `BAGASSE_BL` / `BAGASSE_RL`; rule 5 forbids
a material name in a process definition, so they are carried as `PRIMARY_FIBRE_*` with the original
code named in `source_ref`. The dictation's own material words survive in the section references.

**The dictation states no numeric limit anywhere** — not one band in 830 lines. So every test on the
dictation map freezes no band and every result on it is `no_spec`. **That is the finding, not a
defect.**

## 6. C-32 — the approver is configurable, and the state is still reachable

Both readings are on file, **neither enabled**, each with its source and the cost of adopting it:

| reading | role | source | consequence |
|---|---|---|---|
| `GM_APPROVES_EVERY_LAB_SUBMISSION` | `gm` | lab dictation §15, stated by the factory | the GM carries every lab decision; the comparable operator case was rejected at ~400 open approvals |
| `SUPERVISOR_ACCEPTS_LAB_RESULT` | `supervisor` | `ROLE_AND_APPROVAL_MODEL §2` — the matrix ticks "Accept a lab result as final" for Lab and Supervisor and **not** the GM | the GM loses sight of lab submissions, which the factory asked for directly |

A partial unique index makes two enabled readings **unwritable**, and a test proves it.

**While C-32 is open, a decision from EITHER named role is accepted and the row records which reading
authorised it** — `lab_decision.authorised_under_reading` plus `reading_was_enabled`. A role named by
neither is refused, and the refusal says *"C-32 is open and neither reading names that role — the two
readings on file name gm or supervisor. Both are carried; neither has been chosen."*

**The alternative was refusing every decision until C-32 is answered, and that would have recreated
exactly the defect B1 found in `GM_APPROVAL`: a state nothing can reach.** Carrying both makes the
state reachable under either reading without choosing one, and answering C-32 later turns the other
reading's decisions into history rather than invalidating them. Answering it is **one `UPDATE`** —
a test does it and shows the GM then refused and the supervisor accepted.

`lab_decision.seq` is a `bigserial`, not `order by decided_at`. B6 learned that the hard way:
`now()` is frozen for a whole transaction, so two decisions tie and the later one is lost.

## 7. The control room's Lab-failures band was a false record, and now is not

`src/api/controlRoom.ts` carried:

> *"The laboratory subsystem is not built. `lab_sample`, `lab_test` and `lab_result` do not exist
> yet, so there is nothing to fail a spec."*

That was true and honest when C9 wrote it. **After B5 it is a false statement about the system's own
state** — rule 7 in the other direction — so the band is wired to `v_lab_result_current` and
`labIssues` changed from `Band<never>` to `Band<LabFailure>`.

**It selects `verdict = 'fail'` only.** `no_spec` in a failures band would render *"the factory has
not stated a limit"* as *"something is wrong"*, which is the specific lie `LAB_MODEL §9` and TBD-13
exist to prevent. `invalid` is excluded for the same reason. Superseded versions are filtered out of
the band and stay in the record: a failure that was retested and passed is history, not an open
problem, and `v_lab_result_history` still shows both.

Criterion 62 forbids a zero for an **unbacked** band. A zero here now means "no lab result has
failed", which is a fact.

`tests/controlRoom.test.ts`'s `releasedWith: 'B5'` assertion went red and was **rewritten, not
deleted**: it now asserts that nothing is still released-with-B5, that the band reads the view, and
that `no_spec` cannot reach it.

**The invariant-8 scanner caught me.** A comment I wrote saying *"until 23 Aug"* tripped the
hard-coded-process-length scan (`src/api/controlRoom.ts: found 1, allowed 0`). Reworded to "before B5
