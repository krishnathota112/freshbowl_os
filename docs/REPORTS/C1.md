### `TimeLabel` — and where TBD-50 lands

`TIME_CONTRACT §3.2` predicted this precisely: *"TBD-50 bites only when an instant is formatted into
factory-local wall clock, which happens in `TimeLabel` (C1)."*

Registers 2 and 3 — `Day 5 · H126` and `of <baseline>` — are arithmetic on an hour index and need no
zone, so **they always render**. Register 1 is the wall clock, and it needs both an instant and a
zone to be true. When either is absent it renders `—` with the **TBD-50** marker, and the marker
explains what would go wrong otherwise.

It does **not** fall back to the viewer's zone, which would render a different weekday for a GM in
another country and slide the whole staircase against the calendar axis. It does not fall back to
UTC either. Rule **E.5** — no invented value — and `UI_DESIGN_SPEC §5`: the stated empty state, never
a plausible substitute.

**No time literal appears in the file.** H0's hour of day lives in `factory_clock`; `TimeLabel` only
ever receives `startAt` as an instant and formats it with `Intl.DateTimeFormat` in the factory zone.
A2 (the criterion, not the step) holds.

### The fixtures are functions, not constants — and they had to be

Two rules collide, and between them they decided the design:

```
A12 · time fixtures derive from book1_hour_grid.json, not from typed-in hours
A1  · the process length appears nowhere in src/        (invariant 8)
```

A file of constants cannot satisfy both: the moment the baseline is written into `src/fixtures/` it
is a typed-in hour **and** a literal in `src/`. So every fixture is a function of a
`FixtureGeometry` the caller supplies — read from the Book1 grid in tests, and from
`process_definition` + `factory_clock` in the gallery. **Nothing in `src/fixtures/` knows how long
the process is**, and a test asserts that by searching the file for the two numbers it must not
contain.

`fixtureStaircase` takes the stagger as a parameter for the same reason, and the test derives it from
the gap between consecutive batches' start dates in the grid.

Runtime checks sit alongside the type check, because a type cannot catch what
`UI_IMPLEMENTATION_PLAN §4` actually forbids — *a fixture containing a state the engine cannot
produce* (also rule E.9). So: every `state` is one of the fourteen in `activity_state`; every
non-actionable state carries a reason; and `varianceMinutes` is **null, not 0**, on anything that has
not ended, because that is what the database returns.

### `Variance` is separate from `HumanDuration`, deliberately

A14's pattern has no room for a direction word, and §8.2 requires one (`1h 14m behind`). So
`humanDuration()` returns a **magnitude** — no sign, no decimal, no unit word — and `Variance`
composes it with the direction. The direction is the caller's knowledge, not the duration's: the
same 200 minutes reads as *late* on a variance and as *remaining* on a rest.

`Variance` also distinguishes `null` from `0`. Null means there is nothing to compare yet, which is
what `variance_minutes` genuinely is before an activity ends; zero means `on plan`, because
"0m behind" is not a sentence.

**A14's regex is anchored here.** The document writes it as `/\d+h( \d+m)?|\d+m/`, which unanchored
would also accept `about 3h, give or take 0.5 hours` — it matches a substring. The requirement is
that raw minutes and decimal hours are *never* emitted, so the whole output is matched.

## 3. ⚠ One deviation from the document, stated rather than buried

**A10 and A11 are specified as ESLint `no-restricted-imports` rules. ESLint is not installed in this
repository** — no `eslint` package, no `@typescript-eslint`, no config file of any generation.
Verified before deciding.

Adding it means three new direct dependencies and roughly a hundred transitive ones, and **on its
own it would still not block anything**: `npm test` runs vitest, so an ESLint rule would have to be
wired into the test script before a violation failed a build. The acceptance document's own framing
for section A is *"Run in `npm test`. A failure blocks the step."*

So both are enforced in `tests/uiFoundations.test.ts` as import-boundary scans over the component
directories. **The assertion is identical and it genuinely blocks; the mechanism differs.** The
boundary table is written as data rather than prose so that adding ESLint later reuses it:

```ts
src/components/primitives  L1        src/components/domain     L2
src/components/node        L2        src/components/composite  L3
```

Forbidden below L4: `api/`, `@supabase/supabase-js`, `@tanstack/react-query`, and any
`routes/` import. The scan asserts it inspected files at all, so a mistyped path cannot make it pass
vacuously.

### A11's wording, and why I followed the architecture document instead

A11 reads *"No component outside `useDensity` reads `useAuth().role`"*. Taken literally that
forbids `RoleGuard` in `App.tsx` — which **A15 requires to exist** — and the role chip in
`AppShell`'s header.

`UI_COMPONENT_ARCHITECTURE §3` rule 4 is precise about the same thing: *"Nothing **below L4** reads
`useAuth()` except through `useDensity()`. Role leaks into layout in exactly one place."* That is
the version I enforced. `components/layout/AppShell` is the application chrome that sits **above**
the routes in that document's own component tree, so it is not L1/L2/L3 and is not scanned.

A second assertion covers the "exactly one place" half: any file mapping `lab_tech` to a density is
a second copy of the rule, and the test requires the list of such files to be exactly
`['src/lib/useDensity.ts']`.

## 4. Left undone, and why

- **Consolidating `api/batch.ts` and `api/batches.ts`.** `UI_IMPLEMENTATION_PLAN §4` puts this in
  C1: both modules export `listBatches`, `getBatch`, `createBatch`, `activateBatch` with different
  shapes, and two sources of truth for the same read will produce two different batch pages.

  **Not done.** The plan's stated reason for the timing is *"before any new screen consumes
  either"*, and that constraint is not breached by anything built here: A10 forbids every component
  in this step from importing `api/` at all, and no new screen was built. It is mechanical churn
  across eight route files, it is not tested by the gate, and doing it last thing carried more risk
  of breaking a working screen than of preventing anything. **It is now the first thing C2 should
  do**, and it is still true that no new screen should consume either module until it is done.

- **The rest of C1's Gallery coverage.** `UI_COMPONENT_ARCHITECTURE §4` rule 5 wants every new
  component to have a gallery section covering *default · loading · empty · blocked · error · both
  themes*. The C1 section covers default, loading and the unresolved-timezone case for `TimeLabel`,
  `HumanDuration`, `Variance`, `Bar` and `Skeleton`. `PlayheadContext` has **no gallery section** —
  it has nothing to render until `HourRail` exists, which is C2.

- **The manual pass.** Section B and the cross-cutting checks in section C are a both-themes,
  375/768/1280 px review. Not run: nothing built here is a screen. The gate for this step was
  section A.

- **A1, A2, A5–A9, A15.** Outside the stated gate. A1 is already enforced by `time.test.ts` and
  passes with the two A2 debts cleared; the others belong to later C steps.

- C2 onward. Not started, per the brief.
