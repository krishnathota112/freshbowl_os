## Three decisions the spec forced

**1 · One deviation per failing field, not one per submission.** `ROLE_AND_APPROVAL_MODEL §3.1`
waives *"one failing condition"* — singular. A supervisor must be able to accept the moisture
reading and refuse the fill height in the same submission, so they cannot share a row.

**2 · `accepted` closes nothing.** §3.1 verbatim: *"deviation stays open on the record and
appears in every downstream GM package."* So accepting waives the **condition**, not the
**record**. `v_deviation_open` exposes two different questions:

```
awaiting_verdict   open, escalated                → the supervisor's queue
stands_on_record   open, escalated, accepted      → what the GM package must show
```

Every GM surface reads `stands_on_record`. A package that treated accepted as closed would be
exactly the report §3.1 forbids.

**3 · Only a *verified* corrective action resolves anything.** Recording "we added water" and
recording "the retest came back in band" are different claims, and only the second closes a
deviation. `add_corrective_action` and `verify_corrective_action` are separate calls with
separate actors, and the verification note is mandatory.

## Protected gates — §3.2 names four; two are markable

| Category | Gate | Marked |
|---|---|---|
| Pasteurisation not achieved | `SENSOR_THRESHOLD` on `TN-HOLD`, `pasteurisation_temp_c ≥ 58` | ✅ |
| Tunnel fill above SOP max | `FIELD_IN_RANGE` on `TN-LOAD`, `fill_height_m`, `sop_direct` | ✅ |
| Ammonia not cleared at tunnel out | **no gate exists** — `TBD-14` records that ammonia appears nowhere in the lab workbook | ❌ |
| Critical severity at a checkpoint | **no severity model exists** on `gate_rule` or a checkpoint | ❌ |

The two that cannot be mapped are registered as **TBD-51**, not guessed. **Consequence worth
stating plainly: until TBD-51 closes, a supervisor can accept-with-deviation on conditions §3.2
says only a GM may pass.** That is a real gap, and marking a gate at random would have hidden it.

The pasteurisation rule ships `is_enabled = false` / `sop_inferred` because C-04 and C-27 are
open. It is marked protected anyway — protection is a property of the gate, not of whether it
fires today, and doing it now means nobody has to remember when it is enabled.

## The test that matters most

Role guards are asserted **in both directions** — an operator refused *and* a supervisor
succeeding on the same call.

That is not belt-and-braces. Until `0015_role_claim.sql` landed this morning,
`current_app_role()` returned NULL for every session, `has_role()` was false for everyone, and
**a deny-everyone policy passed every negative test in the suite.** A negative assertion alone
proves a guard exists; only a matching positive proves it is *discriminating*.

The harness connects as `postgres`, so `asRole()` sets the same JWT claim PostgREST sets. These
proofs exercise the real `current_app_role()` path rather than a stub, transaction-scoped and
rolled back.

## Two things I broke and fixed, and one the tests caught

**I regressed 0016's guards.** Rewriting `submit_activity` to add the deviation rows, I lost the
messages that name the activity and — worse — the **effective-pair** check, which catches a
stated end earlier than an *already-recorded* start (`start_activity` may have written one when
the operator opened the card). Comparing only the two parameters missed it entirely. Both
restored verbatim from 0016. Caught by `recordedActuals.test.ts`, not by review.

**The writer-scan caught my three verdict RPCs**, which is exactly what B1 built it for.
`release_activity`, `hold_activity` and `return_activity` write `batch_activity.state` and are
now in `SANCTIONED` with the reason each is an **actor** transition rather than a gate.

**The H0 rule surfaced a pre-existing incoherence — TBD-52.** Scoping it to the *effective*
start refused a live submission on a batch whose `start_at` is still in the future. That
situation is reachable today: `activate_batch` does not require H0 to have passed and
`start_activity` stamps `now()` with no H0 check, so an activity can carry an `actual_start` a
month before its own batch began. The rule is therefore **scoped to stated actuals only** —
refusing at submit would strand an operator over a value they never typed — and what it exposed
is registered rather than resolved. Whether `active` means "baseline frozen" or "running" is a
factory decision.

## A CI hazard worth naming

The DB-backed suite is **flaky against the session pooler**. Two consecutive full runs with
identical settings gave 224/224 and 222/224, the failures landing in different files each time
and presenting as connection-level errors rather than assertion failures. Parallel file
execution makes it worse — one run produced 15 phantom failures that vanished on re-run. Nothing
in the product is wrong; the harness opens more concurrent sessions than the pooler comfortably
serves. Before CI, either pin `--no-file-parallelism`, cap `poolSize`, or point tests at a
dedicated project.
