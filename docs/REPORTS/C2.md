### The gate: the diagonal, with three real batches

**are** the staircase:

1. each bar starts strictly right of the one before it;
2. every bar is exactly the same width — the same length batch, which is what makes it read as a

## 5. Two defects found and fixed while building this

### September was silently January

`factoryDate` derived the month number by looking the localised **short name** up in an array of
twelve. **`en-GB` renders September as "Sept", not "Sep"**, so the lookup missed — and a
`Math.max(0, indexOf)` fallback turned the miss into **month 01**. For one month in twelve the axis
end-date collapsed to January, the span went negative, and the whole board silently rendered its empty
state instead of the staircase.

It surfaced because the real batches are dated August–September. A default where there should have been
a failure — precisely the pattern rule 2 exists to prevent, in code I wrote to enforce that rule
elsewhere.

Fixed by removing the name-to-number mapping entirely: the ISO date is now built from **numeric**
`Intl` parts, a second formatter supplies the display labels, and unreadable parts **throw** instead of
defaulting. Two regression tests walk all twelve months — one on `factoryDate`, one building a whole
axis in each month and asserting every tick lands inside `[0, 100]`.

### The first calendar tick rendered off the left edge

The axis started at the earliest H0, but ticks are placed on factory-local **midnights**, and the
midnight containing that H0 is earlier than it — so the first tick was at a negative percentage, off
the board. Both ends now snap **outward** to a day boundary, which also makes the board begin and end
on a clean date. Asserted for every month.

## 7. Left undone, and why

- **The manual pass.** Section B is a both-themes, 375/768/1280 px review. The structural halves of
  B.4/B.5/B.7 are automated; the visual halves are not, and cannot be without a DOM environment.
- **Hover summaries on bar segments** (§9.2 — "a one-line summary at that hour: what was happening,
  who, and whether it was on plan"). Each segment carries a `title` with its label and hour range;
  "who" and "on plan" need the actor and the variance per segment, which is C3/C4 wiring.
- **Parallel stream lanes** (§10.1 — "when fibre, straw, nitrogen and yard run at once the rail splits
  into lanes"). The rail is single-lane. Lanes need per-stream segment sets, and the T1∥T2 image they
  exist for belongs with the batch page. Not in C2's two components.
- **`WHERE THE TIME WENT`** (§10.1) is **B4**'s attribution view. Not started, and the rail does not
  fake it — the variance register reads "nothing recorded yet" because nothing has been.
- **Consolidating `api/batch.ts` and `api/batches.ts`.** Still owed from C1 §4. `api/tower.ts` is new
  and reads `v_live_batch` directly, so it did not make the duplication worse, but the two old modules
  are still both there.
- **Because no work history is staged** (A3 §8), every real bar is almost entirely `to_come` and no
  actual rail is drawn. The components handle recorded work — a fixture panel in the Gallery shows the
  plan/actual offset — but the live board cannot show it until that question is answered.
