# REPORT — P0 · The Admin UI can create a valid batch

**23 August 2026.** Built by Claude in-session.

## The defect

`TIME_CONTRACT §1.1` makes `master_batch.start_at` mandatory and `validate_batch` reports
`H0_NOT_SET` as **blocking**. `src/api/batches.ts::createBatch` never passed `p_start_at`, so it
defaulted to NULL on every call.

**Every batch created through the Admin screen was unactivatable by construction.** Every batch
that exists was made by a script passing the parameter directly — which is why 332 green tests
never caught it. Nothing exercised the path a person would actually take.

## What was built

`supabase/migrations/0023_batch_h0_default.sql` · `tests/batchCreation.test.ts` — 8 proofs ·
`NewBatch.tsx` step 0 · `api/batch.ts` clock read.

`create_master_batch` now defaults `start_at` from `factory_h0_instant(p_start_date)` when the
caller supplies none, and **refuses loudly** when the factory clock has no timezone rather than
producing the silent NULL that caused this.

## Why the fix is server-side

The obvious client fix is `new Date(`${date}T${time}`)`. That composes the instant in the
**browser's** timezone. The factory is `Asia/Kolkata` (+05:30), so an admin in any other zone — or
a CI runner on UTC — would silently create a batch whose H0 is hours out, and every derived
timestamp would inherit it.

`factory_h0_instant` already existed and already did this correctly, reading the factory clock for
both the hour and the zone. The server owns the clock; the client asks. A test pins the session to
UTC and asserts the batch still lands at 05:00 Asia/Kolkata — the case that would break a
client-side composition.

## No time override is offered

`Book1.xlsx` shows all three batches starting in the same hour-of-day slot, and no source
describes a batch starting anywhere else. A time input would be a field with no factory behind it.
The screen **shows** the H0 it will produce, with its zone, so it is visible rather than invisible
— and the wizard refuses to advance while the clock has no timezone, because the server would
refuse too.

## The wizard is 5 steps, not 9 — and that is deliberate

The proposed shape was ① Identify ② Materials & Quantity ③ Resources ④ Timeline ⑤ Operator plan
⑥ Lab plan ⑦ Evidence plan ⑧ Review ⑨ Activate.

**Four of those have no backend to write to.** Day-0 configuration is quantities plus structure
*counts* (`STRUCTURE_QUESTIONS`: fibre needed, load capacity, bunker lines, yard piles, mixed
piles, straw piles, straw bunkers, turner piles, tunnels). Specific resources, operator plans, lab
plans and evidence plans are all **per activity**, set through `set_activity_plan` — which is
`ScheduleBuilder`'s job, and `ScheduleBuilder` already does it.

Building steps ③⑤⑥⑦ into the wizard would create four screens that write nothing, which
`KIRO_BUILD_INSTRUCTIONS §1` item 10 forbids. The honest flow is the one the architecture already
implies, and which the client independently described:

```
wizard  →  generate  →  ScheduleBuilder reviews and corrects  →  validate  →  activate
```

Recorded in `UI_IMPLEMENTATION_PLAN §S6`.

## A defect found in the guard itself

Invariant 8 failed on this work, correctly — I had written "552-hour baseline" into prose inside
scanned files. But chasing it exposed something worse in the scanner I wrote at T0:

```ts
new RegExp(`(?<![\d.])(${forbidden.join('|')})(?!\d|\.\d)`)
```

`\d` is not a recognised escape in a **template literal**, so JS collapses it to the letter `d`.
The lookbehind had silently become `(?<![d.])` and the lookahead `(?!d|\.d)`. The guard was
matching `23` inside `0023` — and would match it inside `1234`.

It over-matched rather than under-matched, so nothing slipped past it; but it would have produced
a false failure on any migration numbered `00nn` containing those digits. Rebuilt with
`String.raw`. The enumerated debt counts are unchanged, which confirms the false positives were
only ever hitting migration numbers.
