## 1. What was blocking, and what was not

`s04` seeds an enabled, `dictated` `GM_APPROVAL` entry rule on `TN-LOAD`. B1 evaluated it as written:

```sql
elsif g.kind = 'GM_APPROVAL' then
  -- Evaluated as written: an approval must exist. Nothing can record one. See NOTE 2.
  v_ok := false;
```

No approval could exist, because nothing could record one. **So no batch could ever reach the
tunnel.** B1 was right to report that rather than special-case the gate.

**The approver was never in question.** `§1` gives the GM *"Approves or returns at 4 checkpoints"*,
`§2`'s matrix ticks *"Approve management checkpoint 2–4"* in the GM column and nowhere else, and `§5`
names checkpoint 3 explicitly. What was missing was a place to put the decision.

**The seeded rule is untouched** — not disabled, not edited, not given an exception. A test asserts it
is still enabled, still `dictated`, and still names its checkpoint, so nobody can unblock the tunnel by
weakening the rule instead of satisfying it.

## 2. What was built

```
new   supabase/migrations/0020_management_checkpoints.sql
      · management_checkpoint      batch, checkpoint number, state, opened_at
      · checkpoint_decision        verdict, MANDATORY reason, package snapshot, actor, role
      · checkpoint_package()       the snapshot, assembled from what exists
      · record_checkpoint_decision()   GM only
      · v_checkpoint_status        the latest decision per checkpoint
      · evaluate_gates             GM_APPROVAL branch reads the decision
new   tests/checkpoints.test.ts    12 tests
edit  tests/gates.test.ts          B1's "there is nowhere to record it" clause, now obsolete
```

**Three verdicts**, exactly the three `§5` puts on the screen: `approved` ·
`approved_with_conditions` · `returned`. `approved_with_conditions` **is** an approval — it sits beside
APPROVE on `§5`'s mock, and the conditions live in the mandatory reason, which the snapshot preserves.
**`returned` does not open the gate.**

**The checkpoint number is the rule's, not the code's.** `s04` seeds `'{"checkpoint":3}'`, and the
branch reads it from there — so which checkpoint gates which activity stays a seed change.

**The count of checkpoints is not baked into a constraint.** `checkpoint_no > 0`, not
`between 1 and 4`. The model names four; a CHECK encoding that would be a hard-coded count in the
schema (rule 4), and what actually binds a checkpoint to a point in the process is a `gate_rule`.

without a reason**, and a verdict outside the three is refused.

## 4. ⚠ The snapshot says what the GM was NOT shown

`§5`: *"A package is snapshotted when the decision is made. The GM's approval is bound to exactly what
they saw, not to whatever the data later became."*

`§5` specifies **nine sections**. Five can be assembled from records that exist; four cannot, and
`checkpoint_package()` names them in `sections_absent` with the step that would fill them:

| | Section | |
|---|---|---|
| 1 | PLAN | ✅ from `master_batch` + `batch_material_role` |
| 2 | ACTUAL EXECUTION | ✅ from B4 — headline, worst stream, ranked contributors with person, machine and recorded cause |
| 3 | QUALITY | ❌ **B5** — no versioned lab result, spec or trend exists |
| 4 | EVIDENCE | ✅ named requirements, satisfied against required |
| 5 | DEVIATIONS | ✅ from B2, including accepted-and-still-open |
| 6 | CORRECTIVE ACTIONS | ❌ not assembled into this package |
| 7 | RESOURCE USAGE | ❌ **A5** — machine hours are not derivable |
| 8 | CURRENT POSITION | ✅ counts by state |
| 9 | PROPOSED NEXT STEP | ❌ **A5 + Manager authority** |

**Section 9 is the one that matters most, and it is absent.** `§5` calls it *"the point of the whole
document"* — the proposed vessel allocation and fill heights the decision is actually about. `§5`'s
own `[FACT]`: in S3f the 2.25 m fill height and the 3→4 pooling were both real, both known at that
moment, and both later identified as root causes of a failed batch. **That is the content a GM would
be deciding without today.**

A test asserts the absences are declared and each carries a stated reason, so a future reader cannot
conclude the GM saw quality data that did not exist.

**The snapshot is built server-side, at the moment of the decision** — not passed in by the caller. A
snapshot the client supplies is a snapshot the client can shade.

## 5. A defect the proof caught in its own first run

"The latest decision governs" was written as `order by decided_at desc`. The test recorded a `returned`
and then an `approved_with_conditions` **in one transaction**, where `now()` is frozen — so both shared
an instant, the ordering picked arbitrarily, and the approval lost. The gate stayed shut after being
approved.

Not only a test artefact: two decisions a second apart would tie just as well on a coarse clock.
Fixed with a `bigserial seq`, ordered on that. `audit_event` already does exactly this.

## 6. Two documented tensions, carried not resolved

**Who owns checkpoint 1.** `§1` says the GM decides at **4** checkpoints. `§2`'s matrix says
*"Approve management checkpoint 2–4"*, and checkpoint 1 appears only as a precondition of Admin
activation: *"Activate batch ✅ (requires GM checkpoint 1)"*. Whether checkpoint 1 is the GM's own
decision or something they satisfy elsewhere is not stated the same way twice.

Nothing here depends on it: **only checkpoint 3 has a seeded gate rule**, so only checkpoint 3 gates
anything. The RPC requires `gm` for any checkpoint, which is compatible with both readings. Flagged in
the migration header. **If checkpoint 1 should gate `activate_batch`, that is a new rule and a
decision, not an implementation detail.**

**What opens a checkpoint.** Nothing in `docs/` specifies an opener, so the RPC opens one on first use.
Inventing a trigger that decides when a checkpoint becomes *due* would be inventing process.

## 8. `evaluate_gates` was re-created, and why that is stated loudly

The GM_APPROVAL branch is inside a 200-line function, so `0020` reproduces `evaluate_gates` from
`0012` **with one branch changed and everything else byte-identical**. That is deliberate: a silent
edit elsewhere in a function that decides every state transition is how an engine acquires behaviour
nobody chose.

`gates.test.ts`'s eleven B1 proofs — including `SAME_SCOPE_INSTANCE`, the `ALL_INSTANCES` convergence
and *"only the enumerated functions write `batch_activity.state`"* — all still pass against the
re-created function.
