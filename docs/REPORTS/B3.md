# REPORT — B3 · The event trail

**22 August 2026.** Built by Claude in-session.

## What was built

`mushroomos/supabase/migrations/0018_event_trail.sql` · `mushroomos/tests/eventTrail.test.ts` — 11 proofs

- `fn_audit()` gains a key-column argument and is **attached** — to nine governance tables.
- `audit_event` is append-only, enforced by a trigger rather than only a revoke.
- `advance_batch` writes `gate_opened`, `rest_started`, `rest_released`.
- `v_batch_event` — the chronological stream every batch surface reads.
- `safe_uuid()` — a cast that returns null instead of raising.

## The hole that mattered

`advance_batch` wrote **nothing**. Every gate opening, every rest starting and releasing was
invisible — on the one transition class decided by the server rather than by a person. *"Why did
this open when it did"* had no answer in the record.

**The actor on those events is deliberately NULL.** A gate opening has no human behind it; that is
the entire point of a server-authoritative gate, and recording whoever happened to poll would be a
lie about who decided. `v_batch_event.server_decided` distinguishes that from missing data.

A poll that moves nothing writes nothing — asserted. `MyWork` polls every 15 s, and a settled
batch writing events on every poll would make the trail unreadable within a day.

## Where the trigger does NOT go, and why

Not on `batch_activity` or `batch_activity_value`. Those carry hundreds of transitions per batch
across twelve concurrent batches, each would write a full before/after jsonb, and every one is
**already** covered by a semantic event that says *why*. A row trigger there would bury the trail
it was meant to complete.

It goes where a silent change is a governance problem and the volume is low: who has which role,
what the process says, what the gates are, when the factory starts, and what we have not resolved.

`when (old.* is distinct from new.*)` matters more than it looks — the seeds re-run
`on conflict do update` with identical values on every `db:seed`, and without the guard each run
would write ~130 rows saying nothing changed.

## A latent bug from 0001 that this exposed

`current_app_role()` cast the claim straight to jsonb:

```sql
nullif(current_setting('request.jwt.claims', true)::jsonb -> 'app_metadata' ->> 'app_role', '')
```

The `nullif` guards the **output**. Nothing guarded the **input** — and `current_setting(x, true)`
returns NULL only while the setting has never been defined in the session. Once anything touches
it, it reverts to the **empty string**, and `''::jsonb` raises
`invalid input syntax for type json`.

It stayed hidden because `current_app_role()` was only ever called inside RPCs, on sessions that
either carried a real claim or had never seen one. Attaching the audit triggers calls it on
**every governance write, on every session**, which made it fire immediately. `auth.uid()` has the
guard in the right place; this is now the same shape.

**This would have fired in production**, any time PostgREST left an empty claims string — and
every role check in the system goes through it.

## What I got wrong first

- A `plan_generated` trigger on `master_batch` AFTER INSERT always recorded zero, because
  `create_master_batch` inserts the batch and *then* generates the plan. Every alternative fought
  the shape of the code, so it is **not written** and §5 of the migration says why. Nothing is
  lost: the INSERT audit row carries the full Day-0 config, and the activities are rows.
- A join guarded by `entity_id ~ '^[0-9a-f-]{36}$'` still raised, because a regex in a join
  condition does not constrain when the planner evaluates the cast beside it — `factory_clock`
  audits as `'1'`. `safe_uuid()` is the fix.
- My own test tried to DELETE from `audit_event` to get a clean baseline, and was refused by the
  immutability trigger I had just written.
- The suite passed alone and failed 9/11 in the full run. That was not isolation — it was the
  `current_app_role()` bug above, firing once any earlier file had touched the claim.
