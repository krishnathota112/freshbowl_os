## 1. The correctness point, verified

> *the headline variance is the worst stream, so the contributors shown must come from that stream*

**Correct, and correctly implemented.** `v_batch_variance.variance_minutes` is the worst stream
(B4/0019 — four streams run simultaneously, so summing double-counts wall clock).
`v_variance_contributor.rank` partitions by **batch**, not by stream, so the top-ranked contributor
can sit in a different stream from the headline. `api/batchPage.ts` filters before ranking:

```ts
const inWorstStream = v?.worst_stream
  ? allContributors.filter((c) => c.stream === v.worst_stream)
  : [];
```

and `tests/batchPage.test.ts` asserts it against the staged batches — including that the rank-1
contributor within the worst stream is the one the paragraph names. Without the filter, "most of it
came from X" would name an activity whose minutes are not in the number printed above it.

`0023` and `0024` are both sound. `0023` fixes a real defect — `createBatch` never passed
`p_start_at`, so **every batch created through the Admin UI was unactivatable by construction** — and
fixes it server-side via `factory_h0_instant()` rather than composing the instant in the browser's
timezone. `0024` adds `tbd_marker` so the paragraph can name the conflict instead of presenting a
disputed value as settled.

## 2. 🔴 Gate protection was OFF in the deployed database

**The most serious finding, and it was live.**

`0017` set `gate_rule.is_protected = true` on the two gates `ROLE_AND_APPROVAL_MODEL §3.2` protects,
with a one-off `UPDATE`. But `s04_gates_evidence.sql` opens with

```sql
delete from public.gate_rule where process_activity_id in (...)
```

and rebuilds every rule — deliberately, so the seed is idempotent. And `scripts/db.mjs` runs
**all migrations and then all seeds**. So `0017`'s update ran *before* the rows it updated were
deleted and recreated with `is_protected` back at its `false` default.

Measured on the deployed database:

```
--- the two gates §3.2 protects ---
TN-HOLD  SENSOR_THRESHOLD  pasteurisation_temp_c  is_protected: false
TN-LOAD  FIELD_IN_RANGE    fill_height_m          is_protected: false
protected rules in the whole table: 0
```

**A supervisor could `accept_with_deviation` on the tunnel fill-height gate** — the single thing §3.2
exists to forbid. Latent since B2 shipped, armed and disarmed depending on whether a migrations-only
run happened to be the last thing to touch the table. That is why the B2 suite had been passing.

### The fix — `0025_gate_protection.sql`

Another `UPDATE` fixes it until the next seed run. Putting the update at the end of the last seed
fixes it until somebody adds a later seed file. Both make correctness depend on file ordering.

`0017` already says *"protection is a property of the gate, not of whether it fires today"*. A
property of the row belongs in a trigger that derives it on every write — the same shape `0007`
already uses to copy `responsible_role` onto a generated `batch_activity`.

- `gate_rule_is_protected(activity_code, kind, config)` — the predicate, **one definition**, lifted
  from `0017` unchanged and kept inspectable so "why is this gate protected?" has a readable answer.
- `trg_gate_rule_protection` — `before insert or update`, derives `is_protected` **unconditionally**.
  The caller's value is never consulted, because a caller that could pass `false` is exactly how the
  flag went missing.
- A repair `UPDATE` guarded by `is distinct from`, so a replay writes nothing and `0018`'s audit
  triggers do not log an event per gate saying nothing changed.

`is_protected` is now **server-owned**: no seed, migration, client or hand-written `UPDATE` can turn
it off. Rule 6.

**Proved after a full migrations + seed run** — the run that used to disarm it:

```
protected rules in the whole table: 2
```

A new test locks the *cause*, not just the symptom: it asserts the trigger exists, inserts a copy of
the fill-height rule with `is_protected = false` **explicitly** and gets a protected row back, then
tries a direct `UPDATE ... set is_protected = false` and gets a protected row back. Plus a negative
control — an unrelated gate is not protected, so a trigger that returned `true` always would fail.

**Two of §3.2's four categories are still unmarked**, carried forward verbatim from `0017` so nobody
reads the two as the whole of §3.2: ammonia has no gate (**TBD-14**), and "critical severity at a
checkpoint" has no severity model (**TBD-51**).

## 3. Migration replay was broken

`0024` appended `tbd_marker` to `v_variance_contributor`, a view `0019` owns. `scripts/db.mjs` replays
every migration on every run, so on the next run `0019`'s `create or replace view` was asking Postgres
to **remove** that column:

```
FAIL  0019_variance_attribution.sql
      cannot drop columns from view
```

**The run stopped at 0019 and nothing after it applied** — including 0020 through 0024. Every
migration in this repo is written to be idempotent under replay, and that property was silently gone.

`0019` now does `drop view if exists public.v_variance_contributor cascade;` before its create.
`cascade` is safe: the only dependent view is `v_batch_variance`, which the same file recreates and
re-grants further down. `0024` carries a note explaining that appending a column to a view an earlier
migration owns is only safe if that earlier migration drops first.

Verified by running the full migrate + seed **twice**, second run: `FAILs: 0`.

## 4. Two obsolete assertions, rewritten not deleted

Both were honest records of a world C4 changed, and both named their own successor condition.

**`fieldShell.test.ts` · the A15 guard check.** `/admin/batch/:id` showed up as an unguarded route.
Its redirect detector was `/element=\{<Navigate/`, and the new route uses a named
`<RedirectToBatchPage />` — which it must, because `<Navigate to="/batch/:id">` would send the literal
`:id` and drop the search string, losing the deep-linked hour `?h=` exists for.

The detector now also recognises a component that only navigates — but **not by name**. Trusting a
`Redirect`-shaped name would let any component be waved past the guard check by renaming it, so
`redirectComponents()` reads each component's own body and keeps only those that return a `<Navigate>`
and render nothing else. Same reasoning as the existing `start_url` test, which re-checks that
`Landing` really does redirect by role.

And a new assertion, because the exemption needed one: **an unguarded redirect must land on a guarded
route**, or the redirect launders access to the page behind it and A15 is satisfied by a route table
that leaks. `/sign-in` is exempt by name — an unauthenticated person has to be able to reach it.

*(My first version of this scraped every `<Navigate>` in the file and attributed `Landing`'s
`/sign-in` target to every redirect. Scoped to each component's own body.)*

**`fieldShell.test.ts` · `HourRail` absent from the production build.** This suite had discovered on
its own that C2 built the rail, only the DEV gallery rendered it, and once the gallery left the
production build Rollup dropped it. It recorded that as a flagged exception
(`inProductionBuild: false`) and predicted C4 would make it fail. C4 landed, so the exception is
retired and the claim inverts: the rail is in the production build, its consumer is `BatchPage`, and
it is **still out of the field entry**. That last clause is the one that matters — a rail that arrived
by leaking into the operator's bundle would satisfy a naive "is it present" check.

## 10. Stop and ask

**Nothing blocking.** One thing worth a decision:

`s04_gates_evidence.sql` deleting and rebuilding every gate rule is what made the protection defect
possible, and `CONTRACT_AUDIT §6` item 9 says the seeded gate rules *"were paid for once — do not
regenerate them"*. The delete-and-rebuild is idempotency, not regeneration, so I left it alone and
made protection survive it. If you would rather the seed stopped deleting and used
`on conflict do update` like every other seed, that is a larger change to `s04` and it is your call.
