## 1. What I inherited, and what I changed before applying it

`0019_variance_attribution.sql` was **written but never applied** — no view existed in the database,
no test, no report. Its core reasoning is right and I kept it:

> The obvious implementation is `sum(variance_minutes)` per batch. It is wrong, and wrong in the
> direction that makes a batch look worse than it is. `PROCESS-2026B` is a graph, not a line.

Four streams run simultaneously at Day 7. If the paddy soak runs 40 minutes long while the rotavator
mix runs 30 minutes long **on the same afternoon**, the batch is 40 minutes behind, not 70. Within one
stream activities are sequential and minutes genuinely accumulate. So variance sums **per stream**, and
the batch is as late as its **worst stream**.

I made two corrections before it was ever run. Both the same class of error.

### 1.1 A zero that meant "nothing recorded"

```sql
coalesce(w.stream_variance_minutes, 0)   as variance_minutes
```

A batch with nothing recorded reported **0**, which on a GM's screen reads *on plan*.
`UI_ACCEPTANCE_CRITERIA §E` item 4 fails the workstream for a zero that means "not built", and
`KIRO_BUILD_INSTRUCTIONS §1` item 10 says the same. It is **NULL** now.

### 1.2 Zero and unknown are different answers, and the draft could not tell them apart

The draft aggregated the *contributor* view, which deliberately drops rows whose variance is zero — so
a stream that ran exactly to plan vanished instead of reporting 0. Both of these are real, and they
are not the same finding:

| | | reports |
|---|---|---|
| `MB-DEMO-MID` | four activities measured, every one exactly on plan | **0** — "on plan" |
| `MB-DEMO-EARLY` | no activity has both a planned and an actual end | **NULL** — "not known" |

The per-stream aggregate now reads `batch_activity` directly over every row with a non-null
`variance_minutes`; the contributor list stays non-zero-only. `measured_count` is exposed beside the
headline, because that is what tells a reader whether a small variance means *going well* or
*barely started*.

I also added `rank` to the contributor view — §B4 asks for the **ranked** activities, and a ranking
each caller computes for itself is one that will eventually disagree with itself — and a deterministic
tiebreak on the worst-stream pick, so a headline does not move on its own between two identical reads.

## 3. `cause` is read, never inferred

A deviation summary if one exists, else the gate's own `blocked_reason`, else **NULL**. A test asserts
no `cause` exists that neither of those two sources produced — so the view cannot start explaining
delays on its own.

**NULL is the finding, not a gap.** It says this delay has no explanation on file, which is exactly
the question a GM should be asking. There is a test asserting the staged history *contains* such a
delay, so nobody later coalesces it to "unknown reason" or, worse, to a guess.

## 4. What is still not computed, and is not pretended to be

**A true critical path.** The worst stream is a good proxy — the streams converge on the yard and the
slowest one gates the join — but a cross-stream dependency could in principle make a faster stream
critical. That needs the dependency graph walked properly. It is reported as `worst_stream`, named as
such, and not dressed up as a critical path. `all_streams_sum_minutes` sits beside it so the
difference is visible rather than surprising.

## 5. A gap in B2 this surfaced

Correcting a staging mistake (§STAGING.md §4) exercised `return_activity` → re-submit, and left
**three deviations** on one load: two from the erroneous submission and one from the corrected
re-submission. All three read `open`.

`deviation` is append-only by design — `ROLE_AND_APPROVAL_MODEL §7`: *an accepted deviation stays open
on the record* — and that is right. But **there is no verb for "this deviation was raised on a
mis-keyed value"**. The available RPCs are `accept_with_deviation`, `hold_activity`,
`return_activity`, `release_activity`, `raise_deviation`. Accepting means *this stands and we proceed
anyway*, which is not what happened.

Every factory has the mis-recording case. **Is a mis-key a deviation to be accepted, or a distinct
outcome?** That is a process question, not mine, so it is flagged rather than answered. Until it is
answered, a corrected value leaves stale findings on the record that no verb can close.
