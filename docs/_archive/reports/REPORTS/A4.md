## 1. The blocker · the role claim was declared in 0001 and never populated

`public.current_app_role()` is the only role reader in the system. Every RLS policy, every
`SECURITY DEFINER` guard, `has_role()`, `audit_event.actor_role` — all of them go through it:

```sql
select nullif(current_setting('request.jwt.claims', true)::jsonb
                -> 'app_metadata' ->> 'app_role', '')::app_role;
```

Nothing ever wrote `app_role`. Decoded from a real access token, every demo account carried exactly:

```json
"app_metadata": { "provider": "email", "providers": ["email"] }
```

So `current_app_role()` returned **NULL for every client session, and had since 0001**. A4's
`can_capture_for_activity` starts with `current_app_role() in ('operator','lab_tech','supervisor')`,
which is false against NULL, so it refused all six accounts.

**The mechanism was not missing.** `public.custom_access_token_hook(jsonb)` was written in 0001,
granted to `supabase_auth_admin`, and derives the claim from `profiles.role` — correctly. It is
simply **not switched on**, because that is a dashboard action on a hosted project.
`src/lib/auth.ts` and `AppShell` already say so on screen and fall back to `profiles.role` **for
routing only**. What nobody had noticed is the other half of that fallback's own comment: with the
hook off, *every* role-scoped server check is dead, not just admin writes.

### ⚠ WHAT TO CLICK — and why this did not wait for it

In the Supabase dashboard for this project:

1. **Authentication → Hooks** (left sidebar, under CONFIGURATION)
2. **Customize Access Token (JWT) Claims → Enable hook**
3. Hook type **Postgres** · Schema **public** · Function **custom_access_token_hook**
4. **Save**

That is the whole change. Nothing else on that page matters.

**`0015_role_claim.sql` does not depend on it.** GoTrue copies `auth.users.raw_app_meta_data` into
the `app_metadata` claim of every token it mints — that is where `provider` and `providers` above
come from. So the migration writes `app_role` there, from `profiles.role`, through a trigger that
keeps it in step. Identical claim, identical derivation, identical single source of truth, no
dashboard action.

The two cannot disagree, because both read `profiles.role`. **The hook is not edited, dropped or
replaced** — `CONTRACT_AUDIT §6` item 4 says it must survive, and it does. Enable it anyway: it
recomputes at mint time, so it cannot go stale at all.

```
before 0015   "app_metadata": { "provider": "email", "providers": ["email"] }
after  0015   "app_metadata": { "app_role": "operator", "provider": "email", "providers": ["email"] }
```

The migration **asserts its own result** and fails if any profiled account is left without the
claim — a silent no-op here would leave every authorisation check dead and every later proof
mysterious.

### The escape hatch is gone, as 0004 asked

0004 wrote `or public.current_app_role() is null` into three admin-write policies and said of it:
*"once the hook is enabled the clause is dead code and should be removed."* The claim now exists,
so it is removed, and a test asserts no policy anywhere still allows a write when the role is
unknown.

**Being precise about what that was:** the same block in 0004 also does
`revoke insert, update, delete … from authenticated, anon` on all six batch tables, and a policy
cannot grant a privilege that has been revoked. So the hatch was already unreachable and **this
closed no hole that was open.** It removed a clause reading "if the role is unknown, allow", which
is the opposite of what this step is for. The revoke is untouched.

### `evidence_delete_unbound` — a dead code path in the shipped client

`captureEvidence` removes the uploaded object when the bind fails, so a refused bind does not leave
an orphan:

```ts
} catch (e) {
  await supabase.storage.from('evidence').remove([path]).catch(() => undefined);
  throw e;
}
```

**There was no DELETE policy at all**, so that call silently did nothing on every failure. The new
policy permits deletion of exactly one thing: an object **no `evidence_media` row references**. An
unbound object is not evidence.

A bound object stays undeletable by every client, permanently — `evidence_media` has
insert/update/delete revoked from `authenticated`, so nothing a client can call will ever unbind a
row and make its object removable. Append-only survives.

## 4. The gate, item by item

| §A4 requires | How it is proved |
|---|---|
| **private bucket** | `storage.buckets.public = false` asserted; and the object is fetched on the `/object/public/` route and **refused**, so "private" is behaviour rather than a flag |
| **`evidence_media`** with batch, activity, requirement key, storage path, uploader from JWT, **server** timestamp, media kind | all present. `uploaded_by` asserted equal to the **token's** user id, never a parameter; `uploaded_at` asserted within minutes of now from the **server** clock; `mime_type` and `byte_size` read off the stored object, not sent by the caller |

| **criterion 17** | `NMIX-ROTAVATE`, three named requirements. Two satisfied through the real path; `evaluate_gates(…, 'exit')` returns `fail` and the reason **names the third by its label** — *Ammonium sulphate hand mixing* — not "1 photo missing" |

| **a second user CANNOT satisfy another's requirement — by direct PostgREST call with a valid JWT** | three ways, below |
| **no idempotency key** | none added. It was proposed for offline replay, which is out of scope |

### The second-user refusal, asserted three ways

Every one of these is an HTTP call with a real access token. `postgres` has `BYPASSRLS` and a null
`auth.uid()`, so an authorisation proof made through `pg` would be vacuous.

1. **The lab technician cannot upload into the operator's activity path.** The storage INSERT policy
   refuses it, before any row could exist. That is what makes upload-first safe.
2. **The lab technician cannot bind an object the operator legitimately uploaded.** Belt and braces:
   if only storage guarded this, the RPC would be a second way in. Refused with *Not permitted*, and
   the test asserts nothing was recorded against the lab technician on the operator's activity.
3. **An admin may not capture evidence at all.** `ROLE_AND_APPROVAL_MODEL §2`'s matrix ticks
   *Capture evidence* for Field Operator, Lab Technician and Supervisor only. An admin, who can do
   almost everything else on a batch, is refused. Management **sees** the image (§12); it does not
   create it.

And the control that stops all three passing vacuously: **the lab technician CAN satisfy a
requirement on their own activity.**

## 5. Three defects found while getting the gate green

### 5.1 The suite could not put the project back

`afterAll` did `delete from storage.objects`. Supabase installs `storage.protect_delete()`, which
refuses it: *"Direct deletion from storage tables is not allowed. Use the Storage API instead"* —
because removing the metadata row leaves the bytes orphaned in the bucket. Every proof passed and
the **suite** failed in teardown, leaving **16 objects** behind across two runs.

Cleanup now goes through the Storage API, which is what `evidence_delete_unbound` exists to permit.
The 16 were removed the same way; the bucket is empty.

### 5.2 Two correct tests raced each other

`tests/evidence.test.ts` binds real evidence to the live demo batches, and real storage is not
transactional, so it cannot roll back the way every other suite does. Run in parallel,
`tests/demoBatches.test.ts` observed a satisfied requirement and failed its *"no work history was
fabricated"* assertion. Neither test was wrong.

`fileParallelism: false`. One shared deployed database means one file at a time.

### 5.3 The suite was order-dependent, and it hid behind that

With the files serialised, a different failure appeared: *"Photo before mixing already has 1 of 1
item(s)"*. Two causes, both real:

- **`pickTarget` asked a different question from the server.** It filtered on
  `satisfied_count < min_count`; `bind_evidence` counts **live rows**. A counter left stale by the
  crashed run read as outstanding while the row it should have counted was still there, so the suite
  chose a target the server then refused. It now uses the live-row predicate — the same one the
  server applies.
- **The criterion-17 test picked its activity with `limit 1` and no `order by`**, across three live
  batches, and assumed the one it got was pristine. It now requires **all three requirements
  outstanding** and a fixed order, and says so if none is.

And the durable fix: the suite **sweeps at both ends**. Residue at the start means a previous run did
not finish, so it is swept and **reported on the console**, not cleaned up quietly. Scope is
deliberately narrow — `MB-DEMO-%` only, the codes `demoBatches.test.ts` owns, whose own gate asserts
they carry no evidence. It will not touch a batch a person actually worked.

Two consecutive full runs are green, and the evidence file has now run first and last with the same
result.

### 5.4 A comment claimed a test that did not exist

`tests/http.ts` relaxes TLS verification, and its header said *"`tests/uiFoundations.test.ts` asserts
that neither this flag nor any TLS relaxation appears anywhere in `src/`."* **No such test existed.**
It does now — `NODE_TLS_REJECT_UNAUTHORIZED`, `rejectUnauthorized: false` and `strictSSL: false` are
scanned for across `src/`, and the scan asserts it read files at all so it cannot pass vacuously.
