### The stagger — how "48 hours" and "three positions" are both satisfied

§A3 asks for a 48-hour stagger *and* for one batch early, one mid-yard, one in tunnel hold. Those
cannot both describe three **consecutive** batches: consecutive batches 48 hours apart sit at Day n,
n+2 and n+4, all inside Stage 0.

The 48 hours is the **cadence**. `TIME_MODEL_CONFIRMED §2.4` describes ~12 batches alive at once, a
new one every 48 hours. These three are three *of those twelve*, not the first three — their H0s are
0, 8 and 16 days back, which are **0, 4 and 8 multiples of the cadence**. The cadence is honoured
exactly and the positions land where §A3 asks. A test reads the cadence from
`docs/source/book1_hour_grid.json` (the gap between consecutive Book1 batches) and asserts every H0
is a whole multiple of it.

## 6. Two defects this step found

### The role bindings were hard-coded, and one code did not exist

`s11` first bound `STRUCTURAL_STRAW` to `PADDY_STRAW`. **There is no such material** — the codes are
`PADDY_PUNJAB` and `PADDY_LOCAL`. So the role went unbound, and `generate_activity_plan` skipped the
entire straw stream exactly as it is designed to when a role has no material: **ten activities absent,
silently, with no error.** Batches had 90 activities instead of 100.

Now the bindings are **read from `material_role_eligibility.is_default_lead`**, which removes the
whole class of mistake and keeps rule 3 — changing which material leads a role is a change to the
eligibility seed, not to this file. A test asserts no template activity is missing from any demo
batch, and that every role with a default lead is bound.

**The same bug was in `tests/db.ts`.** Every B1 gate test had been running without the straw stream
since C1. It did not invalidate the T1→T2 proof — the yard and turner stream is independent — but the
convergence gates that wait on the straw stream had nothing to wait on. Fixed the same way.

### The vessel allocation was not idempotent, and the gate test caught it on the second run

Found while re-running `npm run db:seed` to confirm the seed was a no-op. It was not. Section 7 only
ever **assigned**, so on a second run it re-chose every destination — the "not already taken by this
batch's same step" check excludes a vessel the row *currently holds*, so every bunker shifted — while
`coalesce(source_location_id, src)` **kept the stale source**. Three reloads ended up pointing at the
bunker they came from, and `validate_batch` reported `SAME_VESSEL` on all three batches.

The A3 gate test failed with seven blocking findings, which is exactly what it is for.

Section 7 is now a **full recompute**: it clears every demo vessel assignment and reallocates. The
greedy pass is deterministic — fixed iteration order, always the lowest free code — so a full recompute
gives the identical result every run, which a partial pass cannot. Destination and source are written
together from the same pass, so the pair cannot drift. A guard refuses to reallocate if any activity has
recorded work, since that would rewrite where work actually happened.

Verified by running `db:seed` three more times: `s11` stays green, blocking findings stay empty, and the
allocation is byte-identical.

### `cancel_batch` was caught by B1's own writer test

Adding it made `tests/gates.test.ts` fail with *"A new writer of `batch_activity.state` appeared"*.
That is the test doing its job. It is now in `SANCTIONED` with its reason: an actor transition, with a
mandatory reason, terminal so no gate can follow it, and it deliberately leaves `COMPLETED` and
`SKIPPED` untouched.

## 7. Vessels — allocated, and the capacity was checked before trusting it

`validate_batch`'s `VESSEL_DOUBLE_BOOKED` treats a vessel as held for **±2 days around every activity
start**. With three concurrent batches that is a real constraint, so I computed the peak before
seeding: **7 bunkers** in the worst 48-hour window against **11 recorded**, and the three tunnel loads
are 192 hours apart so they never contend. Feasible, with room.

The allocation is a greedy pass in planned-instant order across all three batches, taking the
lowest-coded free vessel. Two things make it trustworthy rather than lucky:

- **It is stricter than the check it satisfies.** The seed ignores batch status; `validate_batch` only
  compares against batches already *active*. So the allocation still holds with all three running,
  and a test asserts that directly.
- **It raises rather than overbooking.** If the recorded fleet could not host the stagger, the seed
  stops with the vessel kind, the step and the instant. That is a capacity finding about the factory,
  not something to paper over.

**No YARD destination is assigned**, deliberately, and a test asserts it. The factory records exactly
**one** YARD location, so a yard destination would make every pair of concurrent batches collide on
it. `validate_batch` requires a destination for `BUNKER` and `TUNNEL` only, and it is right to: yard
piles are `scope_label` plus the movement rule's `creates_locations`, and turning them into occupancy
is **A5**. The ±2-day heuristic is itself A5's to replace — at twelve concurrent batches it would
demand ~84 bunkers against 11.
