## 1. The gate, met

> three piles, T1 completed **out of order** (pile 2 first), pile 2's T2 becomes `READY` while
> piles 1 and 3 are still in T1 — as an automated test.

```
✓ SAME_SCOPE_INSTANCE — criterion 15, the T1 to T2 rule >
    pile 2 T2 goes READY on pile 2 T1 alone, with piles 1 and 3 still in T1   8154ms
```

What the test asserts, in order:

1. `turner_pile_count` is read **from the batch's Day-0 config**, not written as a constant, and
   there are that many T1 and T2 instances.
2. **`TR-T1` and `TR-T2` sit on the same `rel_day`.** This is the assertion that makes the test
   discriminating: the barrier that used to govern state opened work when every activity on every
   *earlier* `rel_day` was complete, so it could not tell T1 from T2 at all — it would have opened
   all three T2s at the same moment as the T1s, before a single pile had been turned. Every
   assertion below fails against that engine.
3. All three T1s open. All three T2s are `LOCKED`, each carrying `Locked — T1 not complete on
   Pile n of 3` — its **own** pile named in its **own** reason.
4. Pile 2's T1 is completed **first**, through the real path: `mark_evidence` for each named
   requirement, then `submit_activity`.
5. Pile 2's T2 is `READY`.
6. Piles 1 and 3 are untouched — T1 still `READY`, T2 still `LOCKED` for its own reason.

And its counterpart, so the two bindings are shown to behave differently rather than assumed to:

```
✓ an ALL_INSTANCES gate downstream of the piles waits for every pile   8117ms
```

`P1-BUNK-LOAD`'s entry rule is `PREDECESSOR TR-T2 ALL_INSTANCES` — pooling needs them all. With

## 2. What was actually wrong

122 correct gate rules, read by nothing. State moved on this, in `advance_batch`:

```sql

and earlier.state not in ('COMPLETED','SKIPPED')
```

A global day barrier. It appears in no seed and no specification, and it is the `ALL T1 → ALL T2`

`evaluate_gates(activity, 'exit')`.

## 3. The engine

`evaluate_gates(activity, phase)` is **pure** — declared `STABLE`, writes nothing, and a test
asserts both. So "why is this locked?" and "should this open?" are answered by the same code
rather than by two that agree today. `advance_batch` is the only place a gate-driven state write
happens.

**Four verdicts, not two.** `pass` · `fail` · `skipped` (the rule disabled itself) ·
`unevaluable` (no verdict can honestly be reached).

### The six families §B1 names, against the ten kinds `s04` and `s05` actually contain

| §B1 family | Kinds | Rows | How it is decided |
|---|---|---|---|
| `PREDECESSOR` | `PREDECESSOR` | 35 | `ALL_INSTANCES`, `ANY_INSTANCE`, `SAME_SCOPE_INSTANCE` |
| `COMPOSITE` | `BOTH`, `EITHER_OR` | 3 | all sub-rules / any sub-rule |
| `TIME` | `DAY0_DURATION`, `ELAPSED_TIME` | 8 | server clock against `unblocks_at`, or against `actual_start + hours` |
| `EVIDENCE` | `EVIDENCE_COMPLETE` | 29 | no named requirement with `satisfied_count < min_count` |
| `LIMIT` | `FIELD_IN_RANGE`, `SENSOR_THRESHOLD` | 8 | the recorded value against `sop_min`/`sop_max`, **subject to C-28** |
| — | `MACHINE_STINT_CLOSED`, `GM_APPROVAL` | 39 | see §5 |

`SAME_SCOPE_INSTANCE` matches on **`instance_no`**, not on `scope_label`: the label is display copy
with the count baked into it (`Pile 2 of 3`) and would break the moment a batch ran a different
number of piles.

**An empty predecessor set is satisfied, under every binding.** Not leniency — a stream whose
material role has no material bound produces no instances at all, because `generate_activity_plan`
skips it, so a gate naming it would otherwise deadlock a batch that was never going to run it.
`gate_predecessor_status` returns `total` so a caller can tell "satisfied because complete" from
"satisfied because absent".

### C-28, honoured

A `FIELD_IN_RANGE` or `SENSOR_THRESHOLD` rule auto-fails **only** when `is_enabled` **and**
`mapping_confidence in ('dictated','sop_direct')`. Otherwise `skipped`. Asserted directly:

```
✓ a disabled rule decides nothing, and C-28 keeps an inferred limit from auto-failing
```

A `FIELD_IN_RANGE` rule that *is* trusted but has no numeric reading yet returns **`unevaluable`**,
not `fail`. A limit cannot be applied to a value nobody recorded, and inventing a verdict there is
the exact failure this product exists to prevent.

### Every blocked card explains itself

`render_gate_reason` substitutes from the rule's own `blocked_reason_template` and then **strips any
placeholder it had no value for**, replacing it with `not recorded` — because `{machine_code}` on an
operator's card is worse than an honest gap. Asserted across the whole batch:

```
✓ every reason a gate produces is fully rendered — no placeholder reaches an operator
```

On the deployed active batch: **0 rows** in a non-actionable state without a reason, and **0 rows**
whose reason still contains a brace.

### Only one place writes state

```
✓ only the enumerated functions write batch_activity.state
```

The scan reads `pg_proc.prosrc` for an `UPDATE` whose own `SET` list assigns `state`, or an
`INSERT INTO batch_activity` naming it. The sanctioned list is exhaustive and each entry states why:

| Function | Why it is allowed |
|---|---|
| `advance_batch` | the only gate-driven writer — it calls `evaluate_gates` and nothing else decides |
| `generate_activity_plan` | the initial insert, entirely `LOCKED`. Not a transition |
| `start_activity` | an actor transition: a person opens `READY`/`RETURNED` work |
| `submit_activity` | an actor transition: a person submits. Delegates the unlock to `advance_batch` |
| `repair_plan_states` | 0010's idempotent repair tool, which then re-derives via `advance_batch` |

A sixth writer appearing fails the test. `activate_batch` is **no longer** on the list — it writes
no activity state at all now.

## 5. The two kinds outside §B1's six families

**Neither was special-cased and neither was ignored. Both were evaluated as written.** That is what
kept this from being a decision.

### `MACHINE_STINT_CLOSED` — 38 enabled `dictated` exit rules

Reason: *"Cannot submit — machine stint on {machine_code} is still running"*. A machine stint is a
`machine_usage` row, which is **A5** and does not exist.

The predicate is *"no open stint exists for this activity"*. With no stint table, the set of open
stints is empty, so the predicate is **satisfied**. That is the honest evaluation, not a bypass: the
lookup is written against the table by name and guarded by a single catalogue check, so **the day A5
creates `machine_usage`, the same 38 rules start biting with no change to this engine.** A test
asserts both halves — that the verdict is `pass`, and that `machine_usage` genuinely does not exist.

### `GM_APPROVAL` — 1 enabled `dictated` entry rule on `TN-LOAD`, checkpoint 3

**The approver is named.** `ROLE_AND_APPROVAL_MODEL §1` gives the General Manager "Approves or
returns at 4 checkpoints", §2 gives the GM row "Approve management checkpoint 2–4", and §5 names
this one: *"Checkpoint 3: Phase-1 → Phase-2"*. So this is **not** the unnamed-approver problem, and
it is **not C-32** — C-32 is about lab submissions and belongs to B5.

**What does not exist is anywhere to record an approval.** No `approval` table, no
`management_checkpoint` table, no RPC, and **no step in `BUILD_SEQUENCE_KIRO.md` owns one.**

So the rule was evaluated as written: an approval must exist, none does, therefore it fails, and
`TN-LOAD` holds carrying its own seeded reason —
`Awaiting GM approval — checkpoint 3, Phase-1 to Phase-2 release`.

### ⚠ The consequence, stated plainly

**A batch cannot reach the tunnel.** `TN-LOAD` will stay `LOCKED` until something can record a GM
decision. This is truthful and it invents nothing, but it is a hole in the demo's back half, and
the demo sentence in `BUILD_SEQUENCE` §"What this honestly delivers" ends at tunnel unloading.

**This needs your decision, and I did not take it.** The options, as I see them:

1. **Assign the GM checkpoint surface to a step.** It is a small table (`checkpoint`, `batch`,
   `decided_by`, `decided_at`, `decision`, `reason`) plus `approve_checkpoint` / `return_checkpoint`
   RPCs. It fits B2's shape — B2 already builds `release` / `hold` / `return` /
   `accept_with_deviation` with a named actor and a reason — but B2 does not mention checkpoints.
2. **Disable the rule** by setting `is_enabled = false` on that one row, which the engine already
   honours, with the conflict recorded. That is a seed change and a decision about workflow, so I
   did not make it.
3. **Leave it failing** and accept that the demo stops at Phase 1.

I have left it at option 3, which is the only one that required no choice.

## 6. What else changed behaviour, and it is worth knowing

Reading the gates for the first time **changed the deployed active batch's state**, in the direction
B1 exists for:

```
                        before B1            after B1
MB-2026-09-20  READY        10                  29
               LOCKED      289 (all batches)    70
               COMPLETED      1                   1
```

29 activities are now available instead of 10, because each one opens when **its own** predecessors
are satisfied rather than when an entire calendar day is. That is more parallelism, and it is the
parallelism the factory actually runs. The two draft batches are entirely `LOCKED`, which is 0010's
rule and is unchanged.

requirement and was previously impossible — the old barrier had no idea what it was waiting for.

## 8. Left undone, and why

- **B1's `ANY_INSTANCE` has no top-level test case**, because no top-level rule uses it. Covered
  only through `YD-NMIX-ADD`'s composite.
- **The rest clock cannot be tested by waiting.** Postgres freezes `now()` for a transaction and
  every proof runs inside one that is rolled back, so a rest window can never elapse on its own
  there. The test driver pushes `unblocks_at` into the past, which is what the passage of time
  would do; it is the only state the driver writes and it is commented as such. A real elapsed-time
  proof needs `scripts/prove-rest-gate.mjs`, which cannot run today — it activates a batch, and
  activation now requires H0, which requires TBD-50. See `docs/REPORTS/A2.md §4`.
- **The GM checkpoint record.** §5.
- Everything from B2 onward. Not started, per the brief.
