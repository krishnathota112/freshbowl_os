### The columns

```
process_definition   baseline_days, baseline_hours      GENERATED from total_days
process_activity     standard_start_hour                hours from H0, point scale
                     standard_end_hour                  NULL where no duration is stated
                     standard_hour_source               'derived_from_rel_day' | 'factory_stated'
process_day          (definition, rel_day) → title      was DAY_TITLES in the client
factory_clock        h0_hour_of_day = 5, timezone = NULL
master_batch         start_at timestamptz               H0
batch_activity       planned_start / planned_end        RENAMED to planned_start_at / _end_at
                     baseline_start_hour / _end_hour    the zone-free hour window
                     variance_minutes                   GENERATED
                     duration_actual_min                converted to GENERATED — see §6
```

### The bug that was fixed

`generate_activity_plan` computed every planned timestamp as `(b.start_date + a.rel_day)::timestamptz`
— midnight in the session's zone. H0 is 05:00, so **every planned timestamp in the system was five
hours early**, consistently, on all 300 rows. Both occurrences are gone. Planned instants are now
`H0 + baseline_start_hour`, produced by one function, `repoint_batch_activities`, which
`generate_activity_plan` and `set_batch_start_at` both call — so "generating a plan" and "moving
H0" cannot drift apart.

## 4. TBD-50 — stored, not answered

`factory_clock.timezone` exists, is `NULL`, and carries `timezone_conflict_id = 'TBD-50'`. No
value was chosen. The consequences are deliberate and visible rather than silent:

- **`factory_h0_instant(date)` returns NULL** when the zone is unset. It does *not* fall back to
  the server's zone. Asserted.
- **`create_master_batch` therefore writes `start_at = NULL`** unless the caller passes an explicit
  `p_start_at`.
- **`validate_batch` raises a BLOCKING `H0_NOT_SET`** whose message names the open question:
  `H0 is not set. 05:00 factory time cannot be turned into an instant while the factory timezone is
  unresolved (TBD-50)`.
- **`activate_batch` refuses** while that stands. Asserted.
- **The hour axis is unaffected.** All 300 instances carry `baseline_start_hour` in `0 … 528`.
  An hour index needs no timezone.

No `observes_dst` column was invented: an IANA name answers the DST question by itself. The
question is still recorded in `conflict_register` as part of TBD-50.

**H0 = 05:00 is stored, not hard-coded in `src/`.** `factory_clock.h0_hour_of_day = 5`, with
`h0_source_ref` citing `TIME_CONTRACT §3.1`. No time literal was added to `src/`.

### ⚠ Consequence you should know about

Five `scripts/*.mjs` create a batch and then activate it: `demo-prep.mjs`, `test-plan.mjs`,
`check-schedule.mjs`, `prove-acceptance.mjs`, `prove-rest-gate.mjs`. **Their `create_master_batch`
calls still work** — the seven-argument form was dropped and replaced by an eight-argument form
whose last parameter defaults, so positional and named calls are unaffected. **But their
`activate_batch` calls now fail**, with `Cannot activate — H0 is not set. 05:00 factory time cannot
be turned into an instant while the factory timezone is unresolved (TBD-50)`.

I did **not** patch them, because every patch requires choosing a zone. That is TBD-50, and it is
not mine to answer. The failure is loud and names the question. Answering TBD-50 —
`select public.set_factory_timezone('Asia/Kolkata', '…')`, one call — unblocks all five and
backfills nothing silently.

## 6. Two things found on the way

**`batch_activity.duration_actual_min` is GENERATED in the deployed project, but `0004` declares
it as a plain `int`.** A1's replay diff compared type, nullability and defaults — not generation —
so it did not surface. A fresh project would therefore get a *writable* column where the deployed
one is computed. `0011` converts it (guarded: only when it is not already generated), matching the
deployed expression `(actual_end - actual_start)` in minutes. **`0004` was not touched.**

This also settles what A1 flagged as "the precursor of A2's `variance_minutes`": it is not.
`duration_actual_min` is *how long the work took*; `variance_minutes` is *how late it finished*
against the plan. They are complementary and both are now generated.

**`process_activity.rel_day` can be negative.** Only in ROUTE-2026A, and only because its day
numbering is anchored somewhere other than the batch start. Nothing in the repository said so.
